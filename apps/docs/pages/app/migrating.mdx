# Migrating

## From v1 to v2

Deroll v1 is based on Cartesi Rollups v1, while deroll v2 is based on Cartesi Rollups v2.

Here are the changes you should be aware of when migrating from v1 to v2:

### Rollup transport

Deroll v1 communicates with the Cartesi Machine through the **Rollup HTTP Server**, so `createApp` required its `url`:

```ts
// v1
const app = createApp({ url: "http://127.0.0.1:5004" });
```

Deroll v2 talks to the machine directly through a native Node.js binding ([@deroll/rollup](/rollup)) instead of polling the HTTP server, so `createApp` no longer takes a `url`:

```ts
// v2
const app = createApp();
```

The `ROLLUP_HTTP_SERVER_URL` environment variable is no longer used. The remaining options are [`broadcastAdvanceRequests`](/app/create-app) (unchanged) and the new [`appContext`](/app/create-app) default.

### Input data

The data received by an advance handler changed in two ways: the field names and types follow the rollup's `EvmAdvance` input format, and the fields are no longer nested under a `metadata` object — the handler receives a single flat object, with the `payload` alongside the metadata fields.

```diff
-chain_id: number;
-msg_sender: Address;
-epochIndex: bigint;
-input_index: number;
-block_number: number;
-timestamp: number;
-payload: Hex;
+chainId: bigint;
+appContract: Address;
+msgSender: Address;
+blockNumber: bigint;
+blockTimestamp: bigint;
+prevRandao: bigint;
+index: bigint;
+payload: Hex;
```

```diff
-app.addAdvanceHandler(async ({ metadata, payload }) => {
-    console.log(metadata.msg_sender);
-    return "accept";
+app.addAdvanceHandler(async ({ msgSender, payload }) => {
+    console.log(msgSender);
+    return true;
 });
```

Payloads remain 0x-prefixed hex strings (viem's `Hex`), for inputs as well as outputs.

### Handler results are booleans

Advance handlers return a boolean instead of the `"accept"` / `"reject"` strings — `true` accepts the input, `false` rejects it — matching the underlying binding. Inspect handlers now receive the raw query payload directly, instead of an object wrapping it:

```diff
-app.addAdvanceHandler(async (data) => {
-    return "accept";
+app.addAdvanceHandler(async (data) => {
+    return true;
 });

-app.addInspectHandler(async ({ payload }) => {
-    console.log(payload);
+app.addInspectHandler(async (payload) => {
+    console.log(payload);
 });
```

For the same reason `createReport` and `registerException` take the payload directly: `app.createReport(payload)` instead of `app.createReport({ payload })`.

### Output methods are synchronous

In v1 the output methods returned promises, because each output was an HTTP request to the Rollup HTTP Server. The native binding emits outputs synchronously, so in v2 `createNotice`, `createCallVoucher`, the typed transfers, `createOutput`, `createReport` and `registerException` return their results directly — no `await` needed:

```diff
-const id = await app.createNotice({ payload });
+const id = app.createNotice({ payload });
```

### createVoucher is now createCallVoucher

Cartesi Rollups v2 names the voucher output format `CallVoucher` — an on-chain `CALL` to a destination, carrying an optional `value` in wei and the calldata `payload`. Deroll follows: [`createCallVoucher`](/app/create-call-voucher) replaces `createVoucher`, and the `value` and `payload` fields are now required (use `0n` / `0x` when not needed).

```diff
-app.createVoucher({ destination, payload });
+app.createCallVoucher({ destination, value: 0n, payload });
```

With the `value` field, withdrawing the native token is a plain transfer:

```ts twoslash
import { createApp } from "@deroll/app";

// create application
const app = createApp();

app.addAdvanceHandler(async ({ msgSender }) => {
    const id = app.createCallVoucher({
        destination: msgSender,
        value: 1000000000000000000n, // [!code focus]
        payload: "0x",
    });
    return true;
});
```

### Typed asset transfer outputs

Rollups v2 defines dedicated output formats for asset transfers, which need no manual ABI encoding: [`createErc20Transfer`](/app/create-erc20-transfer), [`createErc721Transfer`](/app/create-erc721-transfer), [`createErc1155Transfer`](/app/create-erc1155-transfer) and [`createErc1155BatchTransfer`](/app/create-erc1155-batch-transfer). Prefer them over hand-built ERC-20/721/1155 `transfer` call vouchers.

The `@deroll/wallet` `withdraw*` methods now build these typed outputs, to be emitted with the matching `App` method (`withdrawEther` builds a `CallVoucher`, the others the corresponding `ERC*Transfer`):

```diff
-const voucher = wallet.withdrawErc20(token, user, amount);
-app.createVoucher(voucher);
+app.createErc20Transfer(wallet.withdrawErc20(token, user, amount));
```

The ERC-721 and ERC-1155 withdrawals no longer take the application address (`dapp`) as first parameter — the typed formats don't need it.

### Output `appContext`

Every v2 output carries an `appContext`: a free-form `bytes32` applications use to tag outputs, so recipients can filter them. It is optional everywhere and defaults to the zero hash; a default for the whole application can be set on [`createApp`](/app/create-app).

### Change in ERC-20 deposit input

The message format of a ERC-20 deposit dropped the byte of the success flag.
If you use the `@deroll/wallet` module this change is automatically handled for you.

### DAppAddressRelay removed

Now that the input data includes the application address (`appContract`) there is no need to use the `DAppAddressRelay` contract anymore.

### Delegate-call vouchers removed

The delegate-call voucher output type present in earlier Rollups v2 drafts was dropped from the final output format set, along with deroll's `createDelegateCallVoucher`. Use a [call voucher](/app/create-call-voucher) instead.

### Executing outputs on the base layer

In v1 each output type had its own entry point on the `CartesiDApp` contract (for example `executeVoucher`).
In Cartesi Rollups v2 all outputs — call vouchers and notices — share a single Merkle tree and are executed and validated through unified functions on the application contract:

```solidity
function executeOutput(bytes output, OutputValidityProof proof);
function validateOutput(bytes output, OutputValidityProof proof);
```

This mainly affects the frontend or relayer code that executes vouchers, not the advance and inspect handlers you write with deroll.

### GraphQL service deprecated

In v1 the inputs and outputs (notices, vouchers and reports) of an application were queried through a **GraphQL service**.
In v2 the GraphQL service is deprecated in favor of a [JSON-RPC API](/app/quick-start#querying-json-rpc) (for example `cartesi_listInputs`).
This is a frontend or off-chain concern and does not affect the advance and inspect handlers you write with deroll.
